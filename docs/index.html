One window, one project, one key

Cursor stores your BYOK API key once per profile, not per repo. cursor-keys gives every project its own isolated profile so each window automatically uses the right key, even side by side.

zero dependencies node ≥18 encrypted key injection license: MIT
npm install -g cursor-keys

# stop billing the wrong project

Register a project once. Every window you open for it, forever, uses its own key. The status line tells the truth at a glance.

$ cursor-keys add nokia --path ~/Projects/nokia-main-cs Profile ready: ~/.cursor-profiles/nokia $ cursor-keys clone nokia # sign-in, settings, models from main $ cursor-keys set-key nokia # hidden prompt, encrypted write Key set for nokia (encrypted with Cursor safeStorage, round-trip verified) $ cursor-keys status Project Color Windows Key Repo famework-platform-1 #339af0 1 yes ~/Projects/famework-platform-1 jlr_mss #4f8cff 0 no ~/Projects/jlr_mss nokia #845ef7 1 yes ~/Projects/nokia-main-cs

# features

Small tool, sharp edges.

isolated profiles

One --user-data-dir per project, the only way Cursor can hold two keys at once. Extensions and MCP config stay shared.

encrypted key injection

set-key encrypts with Cursor's own safeStorage (Chromium OSCrypt) and writes the profile's secret store. Round-trip verified, never plaintext.

clone your setup

clone copies sign-in, theme, and model config from your main Cursor. New profiles open ready, no onboarding wall.

see the active key

Title bar color per project, a status bar item in every window, and status in the terminal. Three layers of "which key am I on".

wrong-window guard

Companion extension notices when a repo is open in the wrong profile and offers a one-click relaunch into the right one.

zero dependencies

Plain Node ≥18 + sqlite3. Nothing to audit, nothing to break, nothing to update.

# commands

One binary, two names: cursor-keys and ckeys.

commandwhat it does
add <name>register project + create profile
clone <name>inherit sign-in, settings, model config from main Cursor
set-key <name>inject the project API key, encrypted and verified
open [name]launch Cursor with the profile (auto-detect from cwd)
statusprojects, colors, running windows, key configured
doctor [name]health checks: key row, base URL, subagent overrides
wrap --installplain cursor <path> auto-picks the profile
aliases --installper-project shell aliases
install-extensionstatus bar + wrong-window guard inside Cursor
initscan a directory for git repos and register them
configshow or set the gateway base URL
syncre-copy main Cursor settings into profiles (automatic on every open)

# config

Optional. Lives at ~/.config/cursor-keys/config.json.

{
  "profilesRoot": "~/.cursor-profiles",          // where isolated profiles live
  "baseUrl": "https://connect.iobonzai.com/cursor", // your gateway endpoint
  "projects": {
    "acme": { "path": "~/Projects/acme", "color": "#4f8cff" }
  }
}

# why

Three honest reasons.

01

Keys are profile-global, work is per-project

No setting, env var, or extension API can swap Cursor's key per folder. Separate profiles are the only correct mechanism, so cursor-keys makes them effortless.

02

Billing the wrong client is a silent failure

You never notice a wrong key until the invoice. Colors, a status bar item, and a wrong-window guard turn an invisible mistake into an obvious one.

03

Secrets deserve real storage

Keys are written into Cursor's own encrypted secret store with Cursor's own encryption. Not dotfiles, not environment dumps, not READMEs.
